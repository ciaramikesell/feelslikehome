# Phase 1B protected transfer review

The product decision is to reuse V3 and keep Places in My Search. This directory is outside the migrations path. The [originally reviewed SQL](proposed-migration.sql) is retained for comparison. The [implementation migration](../../supabase/migrations/2026-11-18-guest-onboarding-transfer.sql) adds the owner autosave guard and is the SQL used by the current transfer tests. The separate [disable script](proposed-disable.sql) is the proposed database rollback after rollout. The SQL was rehearsed only in isolated local databases. See the [test evidence and remaining rollout checks](test-evidence.md).

## Signup binding

1. A same-origin POST starts signup from the guest review and validates the draft UUID and signup fields. The server generates 32 random bytes rendered as lowercase hex. A first-party `__Host-flh-guest-transfer` cookie holds the UUID and secret, with `Secure; HttpOnly; SameSite=Lax; Path=/` and a seven-day lifetime. Cookie contents and form fields stay out of telemetry, request logs, URLs, and local storage. Browser storage keeps only the draft, including its UUID.
2. The POST calls the usual Supabase password signup using the public key and regular request/session cookie handling. Its only additional auth metadata is `flh_guest_signup_v1`, the hex SHA-256 of UTF-8 `secret:draftUuid:email`. The UUID uses canonical lowercase hyphenated formatting. The email is trimmed and lowercased, with GoTrue's stored email canonicalization checked against the deployed PostgreSQL lowercasing in staging, including Unicode. If canonicalization differs, the binding fails closed and keeps the draft. The redirect is a fixed same-origin continuation. Issue the cookie in a separate preparatory response before any call to signup. A lost signup response, an ambiguous duplicate-account response, or a definite rejection keeps both the draft and the original proof available for retry. An ambiguous response alone has no effect on eligibility.
3. The new AFTER INSERT trigger captures the marker and original search identity in the same transaction that creates the actual auth row. Editing metadata on an existing account or receiving an obfuscated duplicate-signup response cannot create this binding. Signup without the marker bypasses the new insert. The cookie only authenticates a transfer attempt when combined with the authenticated session, an email-confirmed non-anonymous auth row, the matching immutable captured digest, and the same draft UUID. A user may supply metadata at their own signup, so a marker by itself confers no authority.
4. On return from verification, show the current account and an explicit save button. The same-origin save POST rechecks Origin, validates the Supabase user via `getUser()`, and checks the cookie UUID against the draft. It rejects any caller-supplied account or search ID. The handler validates the full priorities and progress payload, then passes only the verified user's ID, the cookie proof, and the canonical payload to the private database function over a parameterized PostgreSQL connection. The function independently checks confirmed identity, the original binding, and ownership. A different account has no matching binding.
5. PKCE and the cookie can be absent when email verification opens a different browser or system Safari instead of the iOS WebView. Return to the original browser profile and sign in to the verified account there. A missing cookie, failed exchange or switched account preserves the local draft and offers an explicit recovery path. Existing users can sign in and continue using their established search. Only a genuine, bound signup can apply this draft. Starting signup again for a different email requires explicit confirmation and replaces the active attempt in this browser. The abandoned attempt expires, and the local answers remain available.

## Validation boundary and request contract

The prior proposal granted execution to `authenticated`. Its shallow SQL checks could be reached directly with a JWT and the draft proof. The revised function lives in the unexposed `flh_guest_transfer` schema and grants execution solely to the dedicated database login `flh_guest_writer`. The function also checks `session_user`, which ordinary clients cannot set to another database login. There is no public function or API-role membership in the writer role. The anon, authenticated, and Supabase service-role JWTs cannot use it even with the right account and proof.

Generate the login password out of band. Store the TLS-verified PostgreSQL connection URL only in a server-only secret for the save handler. Do not use the Supabase service-role key or a shared PostgREST login. Provision the [writer role](proposed-provision-writer.sql) separately and verify inherited PUBLIC access using the [read-only catalog checks](proposed-preflight.sql). An old public overload of the transfer function must be absent before enabling the route. The pool must preserve the writer identity as `session_user`, bind arguments as parameters, and bound connection count and statement time. The grant offers execution of this transfer only, with no direct access to the receipt or application tables. A credential leak would cross the validation boundary, so rotate or disable the writer independently and exclude the credential and proof from logs and tracing.

The JSON POST accepts only `draftId`, `priorities`, and `progress`. Limit the body before parsing. Reject unknown fields, inappropriate types, and excessive nesting before normalization. The app must use a strict schema over V3's current typed fields, catalog keys, tier enums, custom feature shapes, limits, and search-type-specific choices. Validate identifiers and references in tier and order maps against the selected catalog and bounded custom entries. Normalize canonical intent with `prioritiesForExplicitSave` and validate the normalized output before the database call. Preserve unknown house facts through the existing Match semantics. SQL's shape and size checks are defense in depth around this server-only boundary.

| Canonical `p_progress` field | Required server rule |
| --- | --- |
| `schema` | Number exactly `1`. |
| `step` | `review` after Personalize or `basics` after the existing As I Go path. Both must enter the explicit guest save screen. |
| `answers` | Exactly `searchType` and `setupPath`. The former is `home_buy`, `home_rent`, or `apartment_rent` and equals `priorities.onboardingSearchType`. The latter is `personalize` or `as_i_go`. |
| `completed` | Canonical ordered list derived by the server from `onboardingStepsFor(4, state)`. Require the input to cover all eligible steps before the final step and permit the final step to be marked complete on save. Reject unknown, duplicate, out-of-path, or geography steps. |
| `skipped` | Unique subset of eligible optional steps in canonical order. Exclude search type, setup path, and review, and require skipped steps to be completed. |
| `startedAt` | UTC ISO-8601 string of the form `YYYY-MM-DDTHH:mm:ss.sssZ`, with a valid round-tripping value within the draft lifetime. Preserve the canonical value for retries. |

Reject extra fields. Keep canonical progress below 12,000 UTF-8 bytes in its PostgreSQL JSONB text form and priorities below 65,536. The server owns `p_user_id`; SQL owns `context`, `updatedAt`, and `completedAt`. Use a generic unavailable result for identity or proof mismatch. Never return account or search identifiers from the database function.

Guest entry and the save route must default off behind a new server-side flag independent of the existing authenticated V3 flag. Do not expose the guest route or give the app the writer credential until the approved migration and QA pass in the target preview project. Preview readiness checks must fail closed if the private signature or grants are missing. This proposal branch contains only docs and local verification, so it has no guest route to enable.

## Transaction and concurrency

- The function is one PostgreSQL transaction under the normal PostgreSQL READ COMMITTED isolation level. It locks the auth user, private attempt row, profile, and signup-provisioned owned search in that order. The capture trigger is named to run after `on_auth_user_created`. The search UUID, original update timestamp, and original legacy priorities digest distinguish the original seed from a replacement or edited search. No guest path creates a search, and the transaction never calls the active-search fallback.
- The existing nondeferrable foreign keys from `search_members.user_id` to `auth.users.id` and from `search_members.search_id` to `searches.id` make concurrent membership inserts take KEY SHARE locks. FOR UPDATE on these parent rows conflicts with KEY SHARE. If acceptance has acquired its relevant key lock, the transfer returns `retry`. If transfer holds both keys first, acceptance waits and then continues normally. After acquiring both locks, the function checks both membership directions in a fresh statement snapshot. Existing co-buyer/Realtor memberships or an already-switched profile block transfer. The original invitation RPCs and role logic retain their existing grants and behavior.
- The profile row lock serializes search switching and account onboarding updates. The search row lock serializes search edits/deletes and FK-backed writes such as homes and commute destinations. Contention, deadlock detection, or a serialization error rolls back all work in the invocation and returns `retry`. An unexpected error rolls back and returns a transport failure. Ordinary edits can still occur after transfer commits. Test the late-arriving legacy onboarding autosave separately and gate obsolete onboarding sessions at the application boundary before enabling rollout.
- Existing personal preferences are protected with an insert-only operation on the unique `(search_id, user_id)` key. A competing insert that wins results in `conflict`; the transfer never runs an update on the preferences row. Profile completion and the receipt commit in the same transaction. The receipt hashes the canonical PostgreSQL JSONB serialization of priorities and progress. Freeze the request at the time of save so retries use the same content, excluding generated per-request timestamps. An identical replay returns `already_saved` with no writes, including after later user edits. A different payload with the same proof returns `conflict`.
- On `saved` or `already_saved`, clear only the matching local draft and cookie. Route to a protected completion screen that rechecks the current owned search before showing Add Home. Avoid automatically opening import on a replay or after search switching. On `conflict`, `invalid_draft`, `unavailable`, `expired`, `retry`, or a lost response, retain the draft. The client may retry transient failures with bounded backoff and the frozen request.

## Grants, retention, and rollback

- The private schema and receipt table have zero grants to API roles. RLS is enabled with zero policies. The two definer functions pin an empty search path and use qualified database objects. The trigger function grants no API execution. The private function revokes PostgreSQL's default PUBLIC execution and grants only the dedicated writer execution. Existing policies, grants, and invitation functions remain as they are. The migration aborts if the migration principal cannot take the required auth-row lock or create the trigger. Verify the deploy principal and effective privileges before rollout; do not broaden API roles to compensate.
- The attempt row records auth user and search IDs, proof and payload digests, a seed version, and timestamps. It stores no raw preferences, secret, or email. The auth-user FK removes it on account deletion. Search deletion cannot rebind the receipt to a replacement search. A first transfer expires after seven days. The receipt is retained for the account lifetime to make a committed attempt non-repeatable. Expired uncommitted rows are inert and follow the same account-deletion lifecycle.
- Deploy additively with guest entry disabled. The disable script revokes writer execution and private schema usage and drops the signup capture trigger while preserving committed searches, priorities, profile state, and receipts. Disable the app entry first and allow in-flight requests to settle before disabling the database endpoint. If a rollback lands between signup and transfer, retain the device draft and let the authenticated person proceed through ordinary onboarding. A later rollout must reconcile any completion under ordinary onboarding as a conflict. Keep the receipt table through rollback so committed attempts remain recognizable after re-enabling.

## Approval and test gates

- Review the auth trigger, database principal, proof handling, transaction locks, rollback, and legacy autosave boundary before implementation. This is a proposal rehearsed only in the disposable local environment; implementation and hosted rollout still require approval.
- On an isolated real PostgreSQL fixture, test both lock orderings using separate connections for co-buyer acceptance, Realtor acceptance/claim, active-search switching, and concurrent owner priority saves. Assert auth and search FK lock modes, actual constraint definitions in the fixture, RLS and function privileges by role, and zero changes to all other searches and users.
- Inject a failure after the priority insert and before profile/receipt updates, then assert all three rolled back. Test parallel identical payloads, mismatched payloads, lost acknowledgement, retry after a newer edit, search deletion/replacement, stale drafts, and the rollback script. Exercise credential and account switching, duplicate emails, unverified and anonymous identities, and signup without a marker. Extend the test auth shim with the required auth columns and triggers, then use local Supabase separately to verify GoTrue, email callback and PKCE behavior.
