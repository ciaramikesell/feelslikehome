## Why the save boundary needs review

The current onboarding finish sequence awaits priority persistence, then issues a separate profile update. A timeout after one write leaves a retry unable to distinguish its own committed work from preferences saved in another tab. Reusing the upsert can overwrite that row. An insert that ignores conflicts can preserve the row, but cannot tell the caller whether the conflicting row came from the same draft. Checking eligibility and then writing in separate requests also leaves a window for an invitation acceptance or a search switch to change account state.

A sanitized return URL only routes the user. It carries no proof that the authenticated user is the one this browser's draft was intended for. Browser storage and editable user metadata are also insufficient as proof. Passing the draft through verification URLs would expose its contents to navigation history and logging. The signup trigger already creates the account's owned search, so a second search-creation path would be redundant.

## Proposed data flow

1. Point the personal Get Started entry points at an unauthenticated onboarding route. Reuse the V3 screens and transitions with local services and existing normalization, ranking, and custom-feature behavior. Keep invitation, Realtor, and protected destinations on their current paths. Preserve direct sign-in and all current release flag settings. Keep active account sessions on their existing routes.
2. Keep a versioned, short-lived draft in same-origin browser storage. Store onboarding progress, necessary priority answers, an opaque draft identifier, and timestamps. Validate the schema, known sections, field types, size, expiry, and supported upgrades before restoring. Drop invalid or incompatible drafts safely and make starting over explicit. Use a TTL of seven days as a proposed default. Exclude credentials, auth/session tokens, invite secrets, and identity fields. Treat custom text as potentially personal, and explain that others using the same browser profile could see it. Closing the browser retains the draft until expiry, confirmed save, or discard. Clearing site data or verifying on a different browser can prevent resumption from that context.
3. Finish guest review with **Save your personalized search** and **Create your account to keep your priorities and start comparing homes.** Reuse signup and sign-in. The return destination should carry only a same-origin path to a protected continuation. Bind the transfer server-side to the verified account and the specific signup attempt, including when verification interrupts it. For a verification link opened in a different browser or the system browser outside the WebView, offer instructions to return to the original device and sign in there. If the session changes accounts, block transfer and leave the original draft intact. A general sign-in into an established account should continue to that account's existing search. It should offer to keep or discard the unapplied draft, with no automatic merge.
4. Add an authenticated transactional operation, preferably a narrowly scoped security-invoker database function if existing grants support the required locking and receipt. Resolve the caller from the verified session and select that caller's signup-provisioned owned search server-side. Check the protected signup binding, search ownership, current onboarding and search selection, membership and Realtor state, and absence of preexisting personal work. Use existing normalization semantics before writing. The server must reject caller-supplied target IDs and keep anonymous callers out. Confirm how invitation acceptance and search switching serialize with the eligibility check before choosing a lock strategy. If existing operations cannot share the necessary locking checks, bring those changes back for review.
5. Commit the priority row, onboarding completion, and an account-and-search-scoped transfer receipt together. A repeated request with the same receipt must return committed success without rewriting priorities; a different draft must get a conflict and keep its local data. A rollback preserves the draft for retry, and a lost response can be recovered with the same transaction identity. Clear local data only after confirmed persistence. Then introduce Add Home through the existing protected import entry and keep saved preferences editable in My Search.
